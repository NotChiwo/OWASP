| 1 | A05 – Injection | `/login`, line 116: `f"SELECT ... WHERE username = '{creds.username}'"` | Send a username like `admin' --` as the whole WHERE clause gets hijacked — the query becomes `WHERE username = 'admin' --'` and the password check is commented out, logging the attacker in as admin with no password. | Use a parameterized query: `"SELECT ... | 3 | A01 – Broken Access Control | `/notes/{note_id}`, lines 132–138 | Any logged-in user (e.g. Alice) can call `GET /notes/2` and read Bob's note just by changing the id in the URL — there's no check that the note actually belongs to the caller. | After fetching the note, check `row["owner_id"] == user["id"]`; if not, return 404 (not 403, so you don't even confirm the id exists). |
| 4 | A07 – Authentication Failures | `/login`, line 122 (`token = str(row["id"])`) + lines 119/121 (different errors for "no such user" vs "wrong password") | The "token" is just the user's numeric id — an attacker can guess `Authorization: Bearer 1` and be logged in as user 1 (admin) with zero credentials, and the token never expires. Separately, the two different error messages let an attacker enumerate which usernames are registered. | Issue a signed, expiring token (`user_id:expiry:hmac_signature`) verified with `hmac.compare_digest`, and return one generic "Invalid username or password" for both failure cases. |

## Reflection (3–4 sentences)
Which bug would do the most damage in a real app, and why?

*(Draft below — rewrite this in your own words before you submit; it's graded as your reflection, not mine.)*

The plaintext password storage (A04) is arguably the worst, because its damage isn't contained to this one app. A SQL injection or broken access control bug exposes *this* app's data, but a leaked plaintext password list hands attackers working logins for every other site where a user reused that password — email, banking, social accounts — turning one small app's breach into a mass account-takeover event elsewhere. The authentication bug (A07) is a close second, since a token that's just the numeric user id is effectively "no authentication at all" and lets anyone become admin by guessing `1`. Both are worse than the SQL injection in practice because they don't require any special attacker skill — just reading the leaked data or trying a small number.
